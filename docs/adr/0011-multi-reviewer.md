# ADR-0011：归因可以由别人来做，但不能互相信任地覆盖

- 状态：部分实现：角色权限与越权拒绝、复核包导出/导入、textSha 守卫、base 三方合并已落地；reviewer 网页待实现
- 日期：2026-11-11
- 相关：ADR-0001、ADR-0007
- 覆盖的候选特性：多人复核（提案人不必是渲染负责人）

## 背景

归因是整套流程里唯一必须由人读的环节，也是最耗时的人工。它天然适合分给别人做：
一个人读第 1061–1145 章，另一个人读 1146–1230 章。现在做不到，因为：

- yovoice 是**单机单用户**应用：数据目录有 `service.lock`，同一时刻只允许一个进程打开
- 状态存在 SQLite 里，桌面服务只监听 `127.0.0.1`，并且校验会话 cookie 与 `Origin`
- `yovoice serve` 提供 HTTP API 与 MCP，**但不提供界面**（`cmd/yovoice/serve.go` 里没有
  web 目录相关逻辑）

所以"让别人也能改归因"不是加一个页面，而是要先决定**谁拥有数据**。

## 决策

分三种角色，先做包，后做局域网，永不做共享目录：

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| **owner**（渲染负责人） | 全部：闸门确认、渲染、混音、导出 | — |
| **reviewer** | 读归因、改 `speakerId` / `kind`、接受或标记待讨论 | 渲染、改正文、确认闸门、动音色锚点 |
| **listener** | 提词器试听、留下书面意见 | 任何写入 |

**第一步（现在）：复核包。** 导出 `review-pack-<范围>.zip`，内含该范围的 cue、证据、
闸门状态、`textSha` 与角色表；reviewer 在自己的机器上用独立数据目录打开、修改、导出
`overrides.json`；owner 导入。

- 覆盖键沿用脚本时代的 `"章节:段落下标"`，因此 `data/overrides.json` 可以直接导入
- 导入前逐章校验 `textSha`：正文变了就整章拒绝并说明原因，不做部分合并
- 两边都改过的 cue **不自动合并**：两边的值都留为提案，由 owner 逐条接受，界面显示差异
- 每个改动记 `{reviewer, at, from, to}`，审计轨迹不随导入丢失

**第二步（可选，需显式开启）：局域网复核页。** 桌面服务已经是 HTTP + cookie + `Origin`
校验的结构，增加一个只读/受限写的复核页，由 owner 在设置里开启并生成一次性 reviewer 令牌，
写权限仅限 `speakerId` / `kind` 两个字段，并逐条记审计。默认关闭。

**拒绝：共享数据目录。** SQLite 加单进程锁，放到网络盘上会同时失去锁语义与数据安全。

## 后果

- 复核包要能脱敏：正文是版权内容，导出范围与角色表要可控
- `overrides.json` 成为稳定的对外契约，格式变更要带版本号
- 局域网页扩大了本地-only 应用的攻击面，所以默认关闭、令牌一次性、权限字段级
- reviewer 不需要装模型或引擎：复核包里没有音频，只有文本与证据

## 备选方案

- **只让 owner 一个人做**（现状）：安全，但 8,970 行的复核会成为整条流程的瓶颈
- **把整个数据目录放共享盘**：技术上能跑起来一会儿，实际会在并发写入与 `service.lock`
  上出问题，属于不可接受的静默数据损坏风险
