# 三个流：工作流、数据流、用户流

这份文档不列功能，只说明**事情按什么顺序发生、数据以什么身份在流转、人在哪些屏之间移动**，
并据此决定构建顺序。决策依据见 [ADR 索引](adr/README.md)。

## 核心结论：三个流的单位不一样

| 流 | 单位 | 为什么 |
| --- | --- | --- |
| 工作流 | **章** | 闸门按章记状态（正文 sha），一章是一个可交付单位 |
| 数据流 | **cue** | 一条 cue → 一次请求 → 一个 take → 一个剪辑 |
| 用户流 | **一次阅读批次（8–15 章）** | 10 章约 1 万字，能一次装进上下文；逐章切换会让人反复重新进入状态 |

三者不同不是缺陷，但不能混用。**现有界面强制用户按「章」移动，而人实际按「批次」工作**——
这是阅读环节慢的第一个原因。

## 一、工作流流

一次新书的完整路径，横向是阶段，纵向是产物与闸门：

```
[导入] epub/txt ──▶ 章节作品           产物: N 个 story 作品
     │
[选角] 正文 ──▶ 角色表 + 候选映射       产物: cast（可增量）
     │
[音色] design ──▶ 候选锚点 ──▶ 审计 ──▶ 冻结锚点
     │              (ADR-0006)  ↑ 不达标回退
     │
[归因] 逐章 读 → 定说话人 → 确认 ──▶ 章: verified     ◀── 唯一的人工瓶颈
     │              (ADR-0001/0007)
     │
[渲染] verified 章 ──▶ 逐 cue take ──▶ 章: rendered   ◀── 唯一花钱的阶段
     │              (ADR-0010 缓存/续跑)
     │
[验收] 回读 WER / 响度 / 空洞 / 通听 ──▶ 章: qa       (ADR-0013)
     │
[混音] 四层 + 侧链 ──▶ 章: mixed ──▶ m4b              (ADR-0004)
     │
[交付] 归档
```

三条闸门（归因确认、锚点审计、验收通过）都是**拒绝放行**型的，不是提示型的。原因是三处的
失败代价不对称：跳过一次归因，等于用 40 分钟 GPU 渲染一章错误的音色；跳过锚点审计，等于用
45 小时污染整本书的一个人。

**关键观察：整条流的成本都压在最后两个阶段，但错误在第一个阶段就产生了。**

## 二、数据流流

每个边界上「数据以什么身份存在」必须唯一确定，否则会静默出错：

```
正文 ──sha256(章)──▶ textSha        ← 闸门身份：正文一变，归因作废
  │
  └──切分──▶ cue {id, speakerId, text, conf, evidence, kind}
                 │
                 ├──(modelId, anchorRev, text, instruction, cfg, seed)──▶ 缓存键
                 │                                                        (take 身份)
                 └──take{wav, seed, 五个数, LUFS}
                        │
                        └──selected──▶ clip{start, offset, dur, gain, fade}
                                           │
                                           └──mix──▶ m4b
```

四条身份规则：

1. **`textSha` 只由正文决定**，与说话人、音色、渲染无关。所以改归因不使 take 失效，
   改正文使一切失效。
2. **take 身份是纯函数的哈希**，包含 `modelId`、`anchorRev` 与 `seed`。换模型或换锚点必然
   产生新 take，不可能"命中"旧音频——这条防的是最隐蔽的错误：以为在听新版，其实是旧文件。
3. **音频是唯一真值，状态是索引**。库里的 take 文件是事实，`selected` 只是指针；
   索引坏了能重建，文件丢了不能。
4. **派生数据不落库**：进度矩阵、覆盖矩阵、章缝余弦、成本预估全部读时计算（ADR-0012）。
   落库会产生两份会漂移的真相。

现有的一个好设计：前端保存是**350 ms 去抖 + 序号防乱序**，所以 367 次复核修改产生的是
约等于停顿次数的提交，而不是 367 次全量快照。**这条不用改。**

## 三、用户流

按角色分，每个角色只走自己那一段，并且**永远从一个队列进入，不用自己找下一件事**：

| 角色 | 入口 | 循环 | 离开时的状态 |
| --- | --- | --- | --- |
| Owner | 书架 → 当前书 | 看"下一件事"→ 处理 → 回到书架 | 阻塞项从队列消失 |
| Reviewer | 复核包 / 书架 | 批次阅读 → 改派 → 确认 | 章从 `attributed` 到 `verified` |
| Listener | 验收页 | 顺序通听 → 标记问题 | 章从 `rendered` 到 `qa` |
| 系列运营 | 书架 | 新卷复用 → 只做新增角色 | 新书进入流程 |

**"下一件事"是唯一的导航主轴。** 现状是按目录点开、按标签切换，用户必须自己记住
"哪些章还没复核"。改成：书级队列把未完成的动作排成一条，一次只显示最前面的几件，
处理完自动前进。这是 UI 上投入产出比最高的一项。

三个最容易丢失上下文的位置：

1. **批次之间**：读到第 8 章去吃饭，回来只记得"大概读到一半"。→ 阅读进度必须落在批次上，
   并记住光标所在 cue。
2. **改派之后**：改了说话人却不确定有没有漏行。→ 队列把"确认后的下一处可疑"直接推上来。
3. **渲染与验收之间**：渲染完 170 章才发现前 5 章音色不对。→ 先渲一段（1–3 章）验收，
   通过后再整卷，把失败前移到便宜的位置。

## 四、据此的四条优化

### 优化 1：渲染按引擎键分组，不要按章顺序

`internal/engine` 的启动键是
`(可执行文件 | model | family | task | backend | loadOptions | sessionOptions | encoderSamples | config)`。
**键一变就停掉引擎再起一个**，而冷启动在基准里慢 **14 倍**（Qwen3-TTS 1.7B：0.25× vs 3.58×）。

按 ADR-0003 分车道（旁白 Qwen3、角色 Breeze）时，如果按「章」顺序渲染，每章都要在两种模型之间
切换两次 → 170 章 = 340 次重启。正确做法是**按 (model, 会话参数) 分组全局排序**：先把全书旁白
渲完，再渲全书对白。代价是交付粒度变粗（第一批不是"第 1 章完成"而是"全书旁白完成"），
所以折中：**按 10–20 章的批次分组**，一批内部按模型排。

### 优化 2：渲染是逐 cue 的，但缺一层"批次"

现状：`GenerateCue(d, cueID, clipID)` 一次一条，唯一的循环在助手工具里
（`assistant_audio.go`、`assistant_work_tools.go`）。缺的是**第一等的批次渲染**：逐 cue 进度、
单条失败不中断整批、写可续跑清单、命中缓存的直接跳过。

### 优化 3：选角与音色按需推进（lazy cast）

第 1111 章只有 6 个说话人，但现状要求先把 18 个角色的音色都设计完才能开始。改成：
**走到哪一章，只要求那一章的说话人有冻结锚点**。未就绪的角色在渲染队列里显示为阻塞项并给出
"设计这个角色"的直达入口。好处是把"看到第一段成品"的时间从"设计 18 个音色"缩短到
"设计 6 个音色"。

### 优化 4：验收先小后大

先渲染并验收 1–3 章（含一个战斗章），通过后再放开整卷。这批的成本是分钟级，而它能挡住
"模型换错、锚点带错、WER 超标"三类整卷级事故。

## 五、不变量（实现时必须成立）

1. 改正文 → `textSha` 变 → 归因回到 `pending`，且该章所有 take 标记为过期（不删除）。
2. 改 `speakerId` / `kind` → `textSha` 不变 → take 不过期，但该 cue 的 `selected` take 若
   来自旧说话人，则必须重新渲染（**take 身份里要含 speakerId**）。
3. 换锚点 → `anchorRev` 变 → 该角色所有 cue 的缓存键变 → 全部重新渲染。
4. 缓存命中必须是纯函数：同键同音频；不同则视为引擎或模型变了，标版本不符而不是静默使用。
5. 混音只读 `selected` take；任何未选中的 take 都不影响输出。
6. 派生视图不落库；任何落库的派生值都算 bug。

## 六、优化后的构建顺序

按"每个阶段解锁多少下游工作"排序，而不是按功能吸引力：

| 阶段 | 内容 | 解锁 | 为什么要先 |
| --- | --- | --- | --- |
| **P0** | 只读分析脚本：章缝余弦、现有渲染的回读 WER、成本预估 | 回答"现有 22 小时里有多少缺陷" | 零 GPU、零 schema 风险，且结果决定后面怎么排 |
| **P1** | `Book` 容器 + 迁移 + 书架 | 所有跨章视图与队列 | 没有它，进度/覆盖/缝检查无处依附 |
| **P2** | 归因阅读批次 + 证据 + 队列（ADR-0007） | 人工瓶颈 | 唯一的人工环节，300+ 条待复核 |
| **P3** | 批次渲染：按引擎键分组、缓存、续跑（ADR-0010 + 优化 1/2） | 唯一花钱的阶段 | 不分组等于多付 340 次冷启动 |
| **P4** | 验收：WER 回读、响度、空洞、通听（ADR-0013） | 交付质量 | 用已有的转写能力即可，且能挡住整卷事故 |
| **P5** | 角色页：锚点候选与审计 UI（ADR-0006/0008）+ lazy cast | 新书启动时间 | 有审计工具但没界面，人不会用 |
| **P6** | 音频库 take 切换、种子账本（ADR-0009） | 迭代效率 | 现在靠文件名记版本 |
| **P7** | 混音四层与侧链（ADR-0004） | 可听成品 | 数据模型已有 `duckDb`，主要是界面 |
| **P8** | 多人复核包（ADR-0011） | 并行复核 | 等 P2 的界面稳定后再做导出 |

P0 是刻意的：它不改任何东西，只在**已有产物上量出真相**。如果章缝余弦显示 170 章里有 30 处
音色跳变，那 P3/P4 的优先级与设计都要跟着改；先量再建，比建完再发现便宜得多。

## 七、不做

- 实时协同编辑（与单写者 SQLite 冲突，收益不抵风险）
- 通用 DAW 时间线（只需要四层 + 侧链，不需要自由编辑）
- 自动应用归因提议（三次只对一次的实测）
- 云端同步整本书（正文版权与单机锁语义）
- 为"以后可能有很多书"提前做懒加载（先量一次保存耗时，见 ADR-0014 的规模一节）
