# 旧流程实录：epub → 有归因的有声书

从 `/home/siva/ss_audiobook/` 的实际脚本与 skill 的 `references/pipeline.md` 重建，不是复述。
最后一节是它对我自己成本模型的**推翻**——先看链路，再看那条更正。

## 一、真实链路（每一步都对应一个脚本）

```
epub ──extract.py──► data/volN.jsonl        {ch, idx, chapter_pos, kind, speaker, conf, evidence, text}
      │                 ▲ 归因优先级：显式说话标签 → 后一段开头点名 → 两人交替 → 沿用上一句
      │                 ▲ 未定的行 conf<0.5，进人工复核
      │
      ├─ attribution_gate.py ──► data/attribution_state.json    pending→read→attributed→verified
      │                          ▲ build 拒绝为未 verified 的章生成脚本（正文 sha 绑定）
      │
      ├─ build_script.py ──► 逐行请求         {text, instruction, cfg, pause_ms}
      │      ▲ EVENT_MAP 把 (sighs) 这类英文括号事件落到 text
      │      ▲ voice_bible_v5.json 提供每角色的 design / anchor / pace
      │
      ├─ render_breeze.py ──► out_c<N>/ch_<n>.m4b + ch_<n>.timeline.json
      │      ▲ 模型只加载一次；每章一完成就编码成 m4b；已有 WAV 直接跳过（可中断可续跑）
      │      ▲ timeline 记录每句的真实位置，供混音使用
      │
      ├─ render_sfx*.py ──► sfx/<cue_key>.wav    （Stable Audio 3 Small SFX 或 MOSS）
      │
      └─ mix_chapter.py ──► mixed/ch_<n>.m4b     三层：ambience / bed / hit + 侧链
```

关键设计不是"能跑"，而是**每一段都能中断后接着跑**：已完成的行 WAV 与已完成的章 m4b 都会被
跳过，所以一整个 170 章的渲染可以按轮次切、按会话切，丢一个会话只损失一轮。

## 二、工作流适配（这些是踩出来的，不是设计出来的）

### 归因

- 正则提议**三次只对一次**，且在两人对话里会系统性反向（把"对某人说"判成"由某人说"）。
  所以：正则只提议，人读了才定；`conf` 与 `evidence` 一路带到复核队列。
- 复核覆盖键是 `章节:段落下标`，可只改 speaker，也可改 kind（叙述↔对白）。

### 音色设计

- **instruction 是漂移主因**：默认 clone-only、`guidance_scale=1.0`，不给描述性指令。
  加指令只在加粗/喊叫行临时用。
- 锚点音频：干净、对齐、**≤30 s**、归一化到 −18 LUFS，逐字稿必须与音频完全一致。
- **锚点 20–25 词 / 约 8 秒**——这条不是音质要求，是速度要求（见下节）。

### 渲染健壮性

- 每段做响度归一（RMS 到约 −20 dBFS，增益封顶，峰值 ≤0.89）；不做就会出现"句与句之间音量漂"。
- 空 take（`size == 0`）绝不进拼接。
- **短句（<1.2 s）取两条 take**：碎裂句是模型最容易跑偏的地方。
- 身份 QA：与角色锚点的对数谱余弦 < ~0.78 就重取，且**重取用 clone-only + 换 seed**，
  绝不把 design 文本当指令再喂一遍。
- 两条 take 身份差在 0.06 内时，选 2–4 kHz 能量更高的（更清晰、少连读）。

### 五个数字（用来结束争论）

| 指标 | 检测什么 | 健康区间 |
| --- | --- | --- |
| 音色余弦 vs 锚点 | 换人 | > 0.85 |
| 浊音比例 | 气声/耳语 | > 0.80 |
| 2–4 kHz 能量占比 | 辅音含混 | 越高越清晰 |
| 每秒词数 | 拖沓/赶 | 2.2–3.0 |
| 中位 F0 | 音区错（太嫩/太老） | 逐角色目标 |

**但便宜的音色指标会说谎**：对数谱余弦曾判定"Morgan 更像 Kai(0.987) 而不是她自己(0.939)"，
跨性别对比荒谬到不能用。音区必须用自相关 F0 量测渲染结果，别用设计值。

### Colab 会话

- **不要在 Colab 上 detach 渲染**：`nohup ... &` 会在 CUDA graph 捕获后卡在 100% CPU / 0% GPU
  永不前进，两次会话同样地挂、白烧 30 分钟。要在 `colab exec` 前台跑，超时交给远端。
- 靠**续跑**而不是靠切块：整章列表每轮都传，远端 `timeout` 切下一轮，下一轮自动接着做。
- Colab 并发会话上限 2；每轮打包下载未打包的章，丢会话最多损失一轮。
- **不要在单张 GPU 上并行 SFX**：4 个 worker 各加载 7 GB 模型互相争抢，三个挂到超时。
  要扩就扩**会话**（一卡一会话），并行的是**混音**（CPU 侧、按章独立）。

### 文本预处理

- `[Mendacious Coffer]`、`[You have slain...]` 是记忆/属性/法术的**格式**不是台词：
  送去合成前要剥掉 `[ ]` 但保留字词，相邻的 `][` 要分开，否则两段播报粘成一句。
- 点燃是事件、燃烧是场景：火起用 hit，火继续烧用 bed。同理水面是 ambience，落水是 hit。
- 同一个记录上两个 cue 必须是**两种不同声音**；同一事件的重复 cue 只会把电平叠高一倍。

## 三、我之前的成本数字是错的

这是我必须自己更正的地方。

| 来源 | 说法 | 我当时的用法 |
| --- | --- | --- |
| 第三方基准 | Breeze "0.48x realtime warm" | 我把它当成**速度倍率**，算成 22h ÷ 0.48 = **45.7 GPU 小时** |
| skill 实测（A100 40GB） | `fast_all=True` **RTF 0.44–0.49** | —— |
| 生产实跑 | 170 章 / 20.4 h 音频，7 轮，**57.8 计算单元** | —— |

0.48 是 **RTF**（时间/音频），不是"0.48 倍实时"。两种读法差 4 倍以上：按 RTF 算，
20.4 小时音频约 **9–10 GPU 小时**；而**生产实测是整卷 57.8 单元**——余额 265 完全够。

所以之前那句"Breeze 要 538 单元、超出余额 2 倍"是**错的**，来源是我把 RTF 当成了速度。
代价是：我建议你放弃的路径，其实是负担得起的；ADR-0003/0010 里那张表的口径需要重算。

### 附带发现：为什么会有"0.48"与"3.1×"两个说法

两边都对，只是配置不同：

| 路径 | RTF（A100 40GB 实测） |
| --- | --- |
| 官方 `fast_all=True` | **0.44–0.49** |
| 官方 eager（`--no-fast`） | 1.9–3.9 |
| ComfyUI 节点包（无官方 CUDA graph） | 1.11–1.67 |

而且有个**静默的 4 倍陷阱**：出厂的 CUDA-graph 预热档只声明到 **256 token**。锚点一旦超过
约 10 秒（加上文本），图形缺失，每一行都悄悄退回 eager——RTF 从 0.44 变成约 1.9，
**比实时还慢**，日志里只有 fallback 计数器能看出来。锚点保持 8 秒/20–25 词，就是为了躲这个。

## 四、这条链路对照当前 yovoice

| 旧链路 | yovoice 现在 | 缺口 |
| --- | --- | --- |
| `extract.py` epub→jsonl | `manuscript.ts` 的 `readManuscript`/`castRoles` | 缺 `conf`/`evidence` 的产出（规则归因没有置信度） |
| `attribution_gate.py` | `schema.Gate` + `ConfirmRead/VerifyChapter` | ✅ 已实现，但导入不写 gate，新章停在 pending |
| 复核 `章节:段落` 覆盖 | 复核包导出/导入（ADR-0011） | 缺界面入口 |
| `build_script.py` 的 EVENT_MAP | 无 | **缺**：`(sighs)` 这类事件没映射 |
| `render_breeze.py` 续跑 | `render-manifest.json` + 缓存键 | 缺与引擎的实际接线 |
| `timeline.json` | `AudioTimeline` 数据模型 | 缺由渲染产出 timeline |
| 五数 QA | `anchor-audit.py`、`qa-chapter.py` | 缺渲染后逐行 QA |
| `mix_chapter.py` 三层 + 侧链 | `mix_policy.go` + `CheckMix` | 缺真正的混音器 |
| 响度/峰值归一 | 无 | **缺**：这是"音量漂"的根因 |

## 五、因此界面必须能表达的东西

1. 章的闸门状态与"确认已读/校验"动作（否则导入即死路）
2. 每行的 `conf`/`evidence`（否则复核队列无法排序）
3. 锚点长度与是否超 8 秒（否则会踩 4 倍陷阱而不自知）
4. 渲染进度与已完成的章（续跑是这套流程能活下来的原因）
5. 五数 QA 的结果，逐行挂在 cue 上

## 六、归因的人工编辑回路（这是流程真正的核心）

机器/代理产出的归因**从来不是终稿**。旧流程里人工改动被完整记录在 `data/overrides.json`，
现在可以拿它把这件事量化。

### 编辑的数据结构

覆盖键是 `章节:段落下标`，值是两种形态：

```json
{
  "1061:1": "jet",                                  // 只改说话人
  "1062:35": {"kind": "dialogue", "speaker": "jet"}   // 同时把叙述提升为对白
}
```

第二种很关键：`kind` 可改 `dialogue` / `narration` / `thought`，也就是**允许把一句从"叙述"
改成"某人说的"**。只允许改说话人的编辑界面是不够的——旧数据里有 12% 的修正是改 kind。

### 实际发生了什么（实测）

| 观测 | 数值 |
| --- | --- |
| 人工覆盖条目 | **1,382** 条 |
| 涉及章节 | 141 / 170 章（83%） |
| 只改说话人 | 1,212 |
| 同时改 kind | 170（→对白 101、→心声 55、→叙述 14） |
| 改派去向 top | sunny 366、nephis 130、jet 126、morgan 124、mordret 80 |
| 占全部行 | **15.4%**（1,382 / 8,970） |

### 这条数据推翻了 ADR-0002 的一个前提

ADR-0002 的设计前提是"复核面就是 `conf<0.5` 的那 367 条（4%）"。但人工真实改了 1,382 条：

- `conf<0.5` 命中 367 条，占真实错误的 **27%**；
- 也就是说，**按置信度排队能抓到的缺陷不到三成**，其余七成是"置信度很高但判错了"。

原因不难理解：解释器错得自信。两人对话里说话人整体反向时，每一行的 `evidence` 都写着
`alternation`、`conf` 可能 0.8 以上——错误是**成片**的，不是零散的。

所以：

- 按 `conf` 排序应当只是**优先级**，不能当成**范围**；界面必须支持"整章通读后批量改"，
  而不是只让人处理低置信度的那几行（ADR-0007 要的阅读式界面正是为此）。
- 批量操作必须支持"整段/整章改派给某人"和"把这一段整体提升为对白"——成片错误用逐行点击修不动。
- 改派去向集中在 POV 角色（sunny 366）说明默认偏向叙事者：**连续讲述者的默认归属是最先要检查的**。

### 两个把人工量降下来的辅助工具

1. **`dump_chapters.py`**：把章节打印成紧凑场景（可指定章节区间与截断长度），供人或 LLM 通读。
   这是"整章读"的物理前提——没有可读的排版，人就会退化成逐行点。
2. **`audit_dialogue.py`**：拿 epub 里的**引号数量**与解析出的对白行数对账，标出
   `MISSED?`（原文有引号但对白为 0）、`THIN?`（远少于引号对）、`FABRICATED?`（原文无引号却有对白）。
   这是解析器的自检——解析器会**静默漏掉**整章对白，没有这个对账就发现不了。

### 对当前 yovoice 的要求

| 需要 | 现状 |
| --- | --- |
| 只改 speaker | ✅ 阅读页 `1–9`/`0` |
| 同时改 kind（叙述↔对白↔心声） | ❌ **缺**：阅读页只能改说话人 |
| 批量改一段/整章 | ❌ **缺** |
| 整章可读的紧凑排版 | ⚠️ 有两行折叠，但没有 `dump_chapters.py` 那种场景视图 |
| 解析器对账（引号数 vs 对白数） | ❌ **缺**，而且这是导入阶段最该有的是否漏章的检查 |
| 覆盖键兼容旧数据 | ✅ `章节:段落下标` |
